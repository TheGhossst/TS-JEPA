# 1. Physical Environment / Raw Data

## Role

The paper evaluates TS-JEPA on an inverted cart-pole system. The device
state is represented by an RGB frame and the actuator receives a
horizontal force command.

### Configuration

``` yaml
environment: "inverted cart-pole"
state_representation: "RGB frame"
sampling_interval_ms: 1
trajectory_steps: 100
control_policy: "nonlinear dynamic-programming policy"
control_min_N: -20
control_max_N: 20
```

**PAPER-SPECIFIED**

The published paper states that the RGB state is sampled every 1 ms for
100 time steps and that the control command is a horizontal force
generated by a nonlinear control policy. The control optimization is
solved through dynamic programming, with control limits of \[-20, +20\]
N.

### General system dynamics and process noise

The paper's general nonlinear system model is:

``` text
x_i,k+1 = f_i(x_i,k, u_i,k) + n_s,k
```

where `n_s,k` is an i.i.d. Gaussian process-noise vector with zero mean
and variance `N_s`.

**PAPER-SPECIFIED**

The paper does **not** provide a separate numerical cart-pole value for
`N_s` in the simulation description. Do not invent one for a strict
reproduction.

### Target / optimal control-command generation

The target control command is defined by the nonlinear optimal-control
problem:

``` text
u*_i,k = arg min_{u_i,k} J(x_i,k, u_i,k)

subject to:
    x_i,k+1 = f_i(x_i,k, u_i,k) + n_s,k
    u_min <= u_i,k <= u_max
```

with quadratic cost:

``` text
J(x_i,k, u_i,k)
    = 1/2 Σ_{k=0}^{K}
        ( ||x_i,k - x_d||_F^2 + u_i,k^T R u_i,k )
```

where `||·||_F` is the Frobenius norm measuring deviation from the
desired state `x_d`, and `R` is a positive-definite matrix penalizing
control effort.

The paper states that solving this optimization problem through dynamic
programming yields the target control commands.

**PAPER-SPECIFIED**

The paper does **not** provide a numerical `R` matrix for the strict
paper-faithful reproduction. Do not replace this nonlinear
dynamic-programming target policy with LQR.

### Important boundary

The paper does **not** specify a particular CartPole implementation,
linearized matrices, LQR controller, or particular `Q/R` matrices.

Therefore do **not** implement any of the following as if they came from
the paper:

``` text
A matrix
B matrix
LQR controller
specific Q matrix
specific R matrix
```

Those would be implementation choices.

# 6. Target Encoder Ψθ̄

## Role

The Target Encoder processes future states and produces target

``` text

          |
          v
       Ψθ̄
          |
          v
z_i,k+1 ... z_i,k+Kp
```

### Relationship to Context Encoder

``` text
same architecture
initially copied from context encoder
no gradient through target branch
updated using EMA
```

**PAPER-SPECIFIED**

### EMA update

``` text
θ̄ ← η θ̄ + (1 - η) θ
```

with:

``` yaml
ema_decay: 0.99
```

**PAPER-SPECIFIED**

The Target Encoder is therefore not trained through ordinary
backpropagation.

Its parameters are updated from the Context Encoder using EMA.

# 7. Temporal Target Selection

TS-JEPA is a temporal prediction architecture.

It does **not** use a spatial patch-masking mechanism like I-JEPA.

The Context Encoder receives the current state, while future states are
encoded by the Target Encoder and predicted by the Predictor.

``` text
current state
    |
    v
Context Encoder
    |
    v
z_k
    |
    +------ Predictor ------> z~_(k+1...k+Kp)

future states
    |
    v
Target Encoder
    |
    v
z_(k+1...k+Kp)
```

### Important terminology

Do not implement a separate "Masking" neural block.

The earlier description of a standalone:

``` text
[5. Masking (Temporal)]
```

has been removed.

The correct interpretation is **future-state target selection / temporal
prediction**, not an independent masking module.

# 10. Latent Prediction Objective

The objective aligns predicted embeddings with Target Encoder
embeddings.

Conceptually:

``` text
predicted embedding
        |
        v
cosine similarity
        ^
        |
target embedding
```

The paper describes the TS-JEPA objective using cosine similarity.

### Implementation form

For actual minimization in code, use an equivalent alignment loss such
as:

``` python
loss = 1.0 - torch.nn.functional.cosine_similarity(
    z_pred,
    z_target,
    dim=-1
).mean()
```

or equivalently minimize negative cosine similarity.

### Important paper-faithfulness note

The published equation is written as an `arg min` involving the
cosine-similarity expression itself. Taken literally, minimizing the raw
cosine value would favor anti-alignment. For implementation, use a
minimizing form that maximizes cosine alignment.

Therefore:

``` text
paper:
    cosine-similarity objective

implementation:
    a minimizing form that maximizes cosine alignment
```

Do **not** describe `1 - cosine_similarity()` as the exact Python
expression printed in the paper. It is the implementation form used to
preserve the intended alignment direction.

# 11. TS-JEPA Training

## Trainable parameters

``` text
Context Encoder Ψθ       → trainable
Predictor Pφ             → trainable
Target Encoder Ψθ̄       → no gradient
Target Encoder Ψθ̄       → EMA updated
```

### Training loop

``` text
1. Encode current state:
       z_k = Ψθ(x_k)

2. Encode future states:
       z_(k+j) = Ψθ̄(x_(k+j))
       j = 1 ... Kp

3. Predict future embeddings:
       z~_(k+1...k+Kp)
       = Pφ(z_k, predicted commands)

4. Compute cosine-alignment loss

5. Backpropagate through:
       Ψθ
       Pφ

6. Update Target Encoder using EMA
```

**PAPER-SPECIFIED**

# 18. Control-Command Normalization and Runtime Denormalization

The paper states that control commands are pre-processed using z-score
normalization to ensure stable TS-JEPA training.

``` text
u_norm = (u - μ) / σ
```

where `μ` and `σ` are the corresponding training-data statistics.

**PAPER-SPECIFIED:** z-score normalization.

**IMPLEMENTATION CHOICE:** Exact storage/loading code for `μ` and `σ`.

### Runtime command-domain conversion

If the Semantic Actor is trained against normalized command targets, its
predicted output must be converted back to the physical command domain
before actuation:

``` text
u_norm_pred
     |
     v
u_pred = u_norm_pred * σ + μ
     |
     v
physical force in N
     |
     v
actuator
```

The paper states the z-score preprocessing but does not spell out this
inverse transformation as a separate runtime equation. Therefore the
explicit denormalization step is an **IMPLEMENTATION REQUIREMENT** for
an executable implementation, not a separately stated paper
architectural block.

Use the same training `μ` and `σ` at inference. Do not send the
normalized actor output directly to the physical actuator.
